# 未授权访问自动对比 — 设计文档

> 版本：v1（2026-09-12）
> 状态：已实现，随 `--chrome on`（默认）与 `--at 0`（默认探测模式）自动生效

## 1. 背景与问题

ChkApiPlus 第一步用 Playwright 携带用户 Cookie（`-c`）抓到的真实 API 响应是**带认证视角**；而未授权访问漏洞的定义正是"去掉认证后接口仍返回真实数据"。但工具既有流程里不存在无认证视角：

- 第五步 `apiUrlReqNoParameter_api` 会把 `-c` 的 Cookie 写入全局 headers，重放同样带认证（这是既有设计：登录态枚举更多接口）；
- 浏览器捕获的响应与任何重放结果也从未被逐 API 关联比对。

带认证的数据就在手上、却没有一个"去掉认证再看一眼"的环节——这是工具链里离"漏洞结论"最近、却断掉的一环。本特性把它接上。

## 2. 总体方案

```
第一步(Playwright, 带Cookie)              第八步 unauthCheck_api
  browser_api_requests ──────┐              1. 归一化URL（去查询串/锚点）
  BROWSER_*.txt(带认证响应)   │              2. 危险API过滤(dangerApiList)
                             └──────────►   3. 无认证重放（剔除Cookie，GET优先/POST_JSON兜底）
                                            4. 响应内容比对 → 判定
                                                    │
                                    9-未授权访问检测结果.txt + 控制台输出
                                    response/UNAUTH_*.txt（无认证响应留证）
```

要点：

- **自带无认证重放**：复制全局 headers 并剔除 `Cookie` 后请求（GET 优先，非 200 json/xml 再 POST 空 JSON），不依赖第五步的覆盖。
- **仅携带 cookies 时执行**：无登录态时浏览器与重放都是匿名视角，对比无意义，直接跳过。
- **时机在 deal_results 之前**：`UNAUTH_*.txt` 落盘后同样参与第九步的 HAE 规则/敏感信息扫描。
- 配套改动：浏览器捕获的 xhr/fetch URL 会**直接并入第五步探测队列**。此前捕获到的真实 API 只参与 base_url 推导，自身可能从未被直接请求过——并入后每个真实 API 都会被带登录态探测一遍（危险路径仍走既有的 `dangerApiList` 过滤）。

## 3. 判定规则（compare_response）

按顺序执行，先命中先返回：

| 顺序 | 条件 | 判定 | 说明 |
|---|---|---|---|
| 1 | 两侧响应**逐字节一致**，且无认证侧命中鉴权失败标记 | 拦截 | 两侧看到的是同一个"请先登录"壳（如整体不带 cookie 跑时） |
| 2 | 两侧响应**逐字节一致**，且无认证侧为空数据 | 拦截 | 如未登录视角的空列表，无数据价值 |
| 3 | 两侧响应**逐字节一致** | **确认** | 最强证据：无认证拿到的就是认证后的数据 |
| 4 | 无认证响应命中**鉴权失败标记**（两侧不同） | 拦截 | HTTP 状态 200 但业务码拒绝的常见返回（`请先登录`/`unauthorized`/`token invalid` 等） |
| 5 | 双方均为 JSON 且**顶层键一致**，≥80% 字段值相同，且无认证侧有真实数据 | **确认** | 容忍 total/时间戳等少量字段差异 |
| 6 | 双方均为 JSON 且顶层键一致，但字段值差异大 | **疑似** | 键结构相同可能只是通用错误壳，需人工核验 |
| 7 | 非 JSON 文本，长度比在 0.9~1.1 | **疑似** | xml/文本接口的粗判 |
| 8 | 其余 | 差异 | 不输出 |

设计要点：

- **完全一致比对先于鉴权标记的"确认"判定**：真实数据里可能本来就含 `token`/`sessionId` 字段（这本身就是泄露），不能因关键词误杀；但两侧完全一致的**鉴权失败壳**（`_is_denied`）和**空数据**会先被降级为"拦截"，堵住两类假阳性。
- **鉴权标记只作用于无认证响应**，用于区分"业务码 401 壳 vs 数据结构"。
- **疑似不等于确认**：只有"确认"级别才建议直接提交，"疑似"需人工核验。

## 4. 数据对齐

- URL 归一化：`scheme://netloc/path`，去查询串、去锚点、去尾部 `/`。浏览器侧带查询串（`?page=1`），重放侧无查询串，归一化后可对齐。
- 配对优先级：同请求方式优先（浏览器 GET 对 GET 重放；浏览器 POST 对 POST_DATA/POST_JSON），每个浏览器 API 只取首个命中，避免 GET/POST 双计。
- 参与对比的门槛：两侧都为"已落盘的 200 json/xml"（`file_path` 非空），即复用第五步既有的 `BLACK_TEXT` 垃圾响应过滤。

## 5. 产出物

1. 控制台（`print`，实时）：

```
[未授权访问-确认] GET	http://x.x.x.x/prod-api/auth/tenant/list
    带认证: 200 application/json 1234B
    无认证: 200 application/json 1234B (GET重放)
    响应内容完全一致
```

2. `results/<目标>/9-未授权访问检测结果.txt`：同格式全量结果；无命中时写入"未发现可确认的未授权访问"。
3. `getJsUrl_info["unauth_findings"]`：结构化结果（url/method/verdict/detail/两侧元数据与文件路径），供内嵌调用方二次消费。

## 6. 使用方式

无需新参数，但**必须携带登录态**（`-c`），否则本环节自动跳过。最小复现命令：

```bash
python3 ChkApi.py -u http://www.xxx.com -c "your_cookie" --dp 5
```

`--dp 5` 提升浏览器侧 API 捕获覆盖率，间接扩大对比范围。

## 7. 局限性与后续方向

- **重放基于无参 GET/空体 POST**：需要特定参数才返回数据的接口不会命中；后续可把第七步提取的参数用于重放。
- **鉴权标记清单是启发式**：业务壳五花八门（`{"status":"error"}` 等），漏拦只会降级为"疑似"，需要人工把关。
- **判定不出漏洞类型**：确认级命中统一按"未授权访问/敏感信息泄露"处理，越权（水平/垂直）需要进一步改参重放，属于另一特性。
- 浏览器侧响应若被 `BLACK_TEXT` 过滤（如含 `Internal Server Error`）或超过 2MB 未落盘，则该 API 不参与对比。
- 重放请求量：每个已捕获且带响应体的 API 最多 2 次额外请求，相对第五步的组合探测可忽略。
